## 二、建钥（KeyGen）

记塔域编码下的 Rain-3 为 Rain_k(pt)：s ← pt；对 r = 0, 1, 2 依次做 s ← s ⊕ k ⊕ RC_r，记录 x_r = s，s ← s^{-1}（GF(2^128) 求逆），记 y_r = s，前两轮再做 s ← M_r·s；最后 ct = s ⊕ k（`rain_owf.hpp:104–121`）。

建钥（`api.hpp:44–47`，Rain 不带 zero_sboxes 标志，走 else 分支）：反复取 32 个均匀随机字节作 sk = (pt ‖ k)，直到三轮的 S 盒输入 x_r 全不为零（`faest_keys.inc:332–337`）；pk = (pt ‖ ct)。私钥和公钥各 32 字节。签名时重算见证 w = ψ(k) ‖ ψ(y_0) ‖ ψ(y_1)，共 384 位，其中 ψ 是塔域到多项式基的固定 GF(2) 线性映射（`faest_keys.inc:133–135`）。

证明的关系 R′（`owf_proof.inc:754–772`）在多项式基下逐轮写 x′_r · y′_r = 1，其中 x′_0 = ψ(pt) ⊕ k′ ⊕ c′_0，x′_r = M′_{r−1}·y′_{r−1} ⊕ k′ ⊕ c′_r，y′_2 = ψ(ct) ⊕ k′。x·y = 1 推出 x ≠ 0，所以 R′ 是 Rain 原像关系 R 的子集，抽出的见证一定是真原像。

## 五、两条核心关系

**VOLE 关系（理由 C 的正确写法）。** 对每棵树 t、每个 b ∈ [k_t] 和全部 688 行，

q_t[b] = v_t[b] ⊕ δ_{t,b}·u。

推导：验证方的和式等于 ⊕_{j ≠ h} [(j ⊕ h)_b] m_j，按 j 的第 b 位分两种情形展开，再加上 δ_{t,b}·c_t，得 V_t[b] ⊕ δ_{t,b}·u_t ⊕ δ_{t,b}·(u_0 ⊕ u_t) = V_t[b] ⊕ δ_{t,b}·u_0，洞种子 s_{t,h} 正好消掉。把各列拼起来就是 **Q = V ⊕ Δ·u**（论文 §4.1 p.7 写作 q_{i,t} = v_{i,t} ⊕ δ_{i,t}·u_i，与此一致）。被驳回稿写的 V = Δ·u 是错的。经第 4 步修正后，前 384 行变为 K = M ⊕ Δ·w，第 384–511 行是 K = M ⊕ Δ·u（掩码）。

**VOLE 检查哈希的结构。** VH 对固定的 chall1 是 GF(2) 线性映射；在第 512–687 行上是单位阵，也就是说掩码行原样加到输出上。所以对任何 chall1，只要 x[512:688] 均匀，VH(x) 就均匀。这条性质与 VH′ 是什么无关，阶段 02 的局部秩引理要用它。

## 六、AES 的密钥与明文角色（理由 B）

全部 AES 调用都是 E_密钥(明文)：密钥永远是种子（r、树节点或叶种子），明文永远是 iv ⊞ ⟨计数, 调整值⟩。种子从不当明文用。被驳回稿把 F_com 写成 E_{iv⊕⟨a,1⟩}(s)，即以 iv 为钥、以种子为明文，与代码相反。

同一把钥用到的明文互不相同。对固定的 t，用到的调整值是：0（根，钥为 r，计数 t ∈ [τ]）；(d+1)τ + t，d ∈ [k_t]（节点展开，计数 0、1）；(k_t+1)τ + t（叶承诺，计数 0）；2^31 + t（带，计数 0–5）。(d+1)τ + t 是 τ 进制编码，所以不同的 (t, d) 给出不同的调整值；叶承诺的调整值不会等于任何节点调整值（等式要求 d = k_t，而节点的深度 d < k_t）。所有调整值都小于 2^32，lane 加法不溢出到其他 lane。所以同一把钥永远不会以同一个明文被调用两次。

## 七、随机预言的划分

全部哈希都是 SHAKE128 加末尾一个域分离字节，SHAKE 吸收整个输入串，所以末字节不同的调用天然不相交。末字节相同的只有 0x01 一组，用长度区分：h_t 的输入是 16N_t + 1 字节，h_com 的输入是 32τ + 1 字节，三档参数下 N_t 都不等于 2τ（N_t ∈ {32, 64} / {128, 256} / {1024, 2048}，2τ = 42 / 34 / 22）。

## 十、安全游戏的对应

EUF-CMA 游戏：KeyGen 照第二节；签名预言对任意 msg 运行 crypto_sign，**每次新取 ρ**，不缓存、不复用。确定性签名不经对外接口暴露，不在本游戏内，若要覆盖需另行分析。随机预言按第七节的划分建模，AES 建模为理想分组密码，种子作钥。伪造者赢的条件是对一个从未查询过签名的 msg 输出能通过验签的 σ。抽取器要给出满足 R′ 的 (k, y_0, y_1)，OWF 归约成功的条件是 Rain_k(pt) = ct。

另外两项观察。其一，三个实例的 chall1 下，176 位 VOLE 检查哈希矩阵的 GF(2) 秩：全部行为 176，前 512 行为 176，只取前 384 行也是 176；第 512–687 行确为单位阵。这只是三个样本，不是证明。其二，每列存储 96 字节，但签名只传前 86 字节，所以第 688–767 行验证方的 q 不受约束；实测有 2,000–2,500 位不满足 Q = V ⊕ Δu。VOLE 检查只读前 512 行加第 512–687 行的掩码字节，QuickSilver 只读前 512 行，签名也不含这些行，所以它们没有协议含义。这里记下来，免得后面误当成异常。

## 十二、关卡结论与交接

**关卡 00：通过。** 真实协议与时序已定死，并与代码逐位一致；理由 A、B、C、D、G 在协议层面已改正。本阶段不给出任何安全结论。

- 阶段 01：抽取器只用 H₂¹ 查询时刻的信息，从 H 记录反查 h_com 与 h_t 两层，再在 AES 记录里按固定调整值 (k_t+1)τ + t 匹配叶承诺。抽取 u 只需第 0 棵树；其他树用于一致性。
